🐧 codencode AcademySession 6 · Error Handling

Error Handling — try / except / finally 🛡️

What: Wrap risky code in try/except so your program doesn't crash.
When: File reads, user input, API calls, type conversions — anything that could go wrong.
Why: A crash loses data. Handling errors lets you show a helpful message and keep going.
# error_handling.py
# ❌ Crash if file missing
f = open("data.txt")   # FileNotFoundError!

# ✅ Handle it gracefully
try:
    f = open("data.txt")
    content = f.read()
except FileNotFoundError:
    print("File not found!")
except PermissionError:
    print("No permission to read file")
finally:
    print("This always runs")

# Catching multiple + custom message
try:
    age = int(input("Enter age: "))
    if age < 0: raise ValueError("Age cannot be negative")
except ValueError as e:
    print(f"Error: {e}")

# Custom exception
class InsufficientFundsError(Exception):
    pass

raise InsufficientFundsError("Balance too low!")

try/except structure

  • try: — the risky code
  • except ErrorType: — handle specific error
  • except Exception as e: — catch all + inspect
  • else: — runs only if NO error
  • finally: — always runs (cleanup)

Common exceptions

  • ValueError — wrong type/value (int("abc"))
  • FileNotFoundError — file doesn't exist
  • KeyError — dict key missing
  • IndexError — list index out of range
  • ZeroDivisionError — divide by zero
  • requests.ConnectionError — no internet

File I/O & JSON — Reading & Writing Data 📁

When to use files: Saving user data between sessions, storing configs, exporting reports, logging.
Why JSON: JSON is the universal language between Python and the web — all APIs speak JSON.
# file_json.py
# Reading a text file
with open("notes.txt", "r") as f:
    content = f.read()
    # or: lines = f.readlines()

# Writing a text file
with open("output.txt", "w") as f:
    f.write("Hello world!
")

# Appending to file
with open("log.txt", "a") as f:
    f.write("New log entry
")

# JSON — save Python dict to file
import json

data = {"name": "Ali", "scores": [85, 92, 78]}

with open("data.json", "w") as f:
    json.dump(data, f, indent=2)

# Load JSON from file
with open("data.json") as f:
    loaded = json.load(f)

print(loaded["name"])     # Ali
print(loaded["scores"])   # [85, 92, 78]

File modes

  • "r" — read (default, file must exist)
  • "w" — write (creates/overwrites)
  • "a" — append (adds to end)
  • "r+" — read and write

JSON cheatsheet

  • json.dumps(data) → string
  • json.loads(string) → dict
  • json.dump(data, file) → write file
  • json.load(file) → read file
  • Always use with open() — auto-closes file
  • Add indent=2 for pretty printing

REST APIs — Talking to the Internet 🌐

What: An API lets your code talk to another service (weather, currency, maps, OpenAI).
How: You send an HTTP request, the server sends back JSON. The requests library makes this 2 lines of code.
When: Any time you need real-world data your program doesn't have itself.
# api_calls.py
import requests

# GET request — fetch data
url = "https://api.openweathermap.org/data/2.5/weather"
params = {
    "q":     "Kuala Lumpur",
    "appid": "YOUR_API_KEY",
    "units": "metric"
}

response = requests.get(url, params=params)

if response.status_code == 200:
    data = response.json()
    temp = data["main"]["temp"]
    desc = data["weather"][0]["description"]
    print(f"KL: {temp}°C, {desc}")
else:
    print(f"Error: {response.status_code}")

# POST request — send data
payload = {"title": "My Post", "body": "Hello"}
r = requests.post("https://jsonplaceholder.typicode.com/posts",
              json=payload)
print(r.json())     # API echoes back with id=101

HTTP status codes

  • 200 — OK (success)
  • 201 — Created
  • 400 — Bad Request (your fault)
  • 401 — Unauthorized (wrong API key)
  • 404 — Not Found
  • 500 — Server Error (their fault)

Free APIs to practice

  • JSONPlaceholder — fake REST API, no key needed
  • OpenWeatherMap — weather data (free tier)
  • RestCountries — country info, no key needed
  • The Dog API — random dog images
  • CoinGecko — crypto prices, no key needed

Project Ideation — Thinking Before Coding 💡

Most beginners start coding too early. Spending 30 minutes planning prevents 3 hours of rewriting. Every good project starts with answers to 5 questions.
❓
What problem does it solve?
Who suffers from this problem? Is it a real pain or imaginary? Would people pay for the solution?
👤
Who is the user?
Age, tech skill, goal. A 60-year-old user needs a different UI than a developer. Know your user.
⚙️
What are the core features?
List 3–5 must-have features. Everything else is "nice to have". MVP first, polish later.
🔧
What tech do I need?
Frontend? Backend? Database? API? What do you already know vs need to learn?
⚠️
What could go wrong?
Data privacy? API rate limits? Users entering bad data? Scale? Plan for failure early.
💡 Rule: If you cannot explain what your app does in 1 sentence, you're not ready to code yet.

Case Study: LazyApply — Real SRD Analysis 🎯

LazyApply is a job application automation tool. Let's break down its SRD (System Requirements Document) to understand how to plan a real product.

1. Problem Statement

  • Job seekers spend 2–4 hours manually filling identical forms on every job site
  • LazyApply auto-fills LinkedIn, Indeed, Glassdoor etc. with one profile setup
  • Target user: Active job seeker, 20–40, comfortable with browser tools

2. Core Features (MVP)

  • ✅ 1-click job application on major job boards
  • ✅ User profile: contact, resume, custom answers
  • ✅ Application tracker (how many applied, success rate)
  • ✅ Browser extension for seamless integration

3. Tech Stack chosen

  • Frontend: Chrome Extension (HTML/CSS/JS)
  • Backend: Python Flask API + PostgreSQL
  • Auth: JWT tokens
  • Hosting: AWS EC2 + RDS

4. Design Decisions

  • Color palette: #121226 (dark navy) + #6868a6 (purple)
  • Typography: Inter for UI, Poppins for headings
  • Card-based layout for job listings
  • Progress bar for application success rate

5. What could go wrong?

  • Job site HTML changes → auto-fill breaks
  • CAPTCHA blocks automated submissions
  • Users enter wrong data → bad applications
  • API rate limits from job boards

SRD Writing Checklist

  • □ Problem in 1 sentence
  • □ Target user profile
  • □ 3–5 MVP features (no more)
  • □ Tech stack justified
  • □ Data model (what data do you store?)
  • □ Risk & mitigation plan
  • □ Success metric (how do you know it works?)

👨‍🏫 Teacher Demo: Weather Dashboard + Expense Logger

Combining APIs, file I/O, and error handling

# weather_expenses.py
import requests, json, os
from datetime import datetime

# ── Weather ──────────────────────────
def get_weather(city):
    try:
        r = requests.get(
            "https://wttr.in/{city}?format=j1".format(city=city),
            timeout=5
        )
        r.raise_for_status()
        w = r.json()["current_condition"][0]
        return f"{w['temp_C']}°C, {w['weatherDesc'][0]['value']}"
    except Exception as e:
        return f"Error: {e}"

# ── Expense Logger ───────────────────
FILE = "expenses.json"

def load_expenses():
    if os.path.exists(FILE):
        with open(FILE) as f:
            return json.load(f)
    return []

def add_expense(item, amount):
    expenses = load_expenses()
    expenses.append({
        "item": item, "amount": amount,
        "date": datetime.now().strftime("%Y-%m-%d")
    })
    with open(FILE, "w") as f:
        json.dump(expenses, f, indent=2)
    print(f"Saved: {item} RM{amount}")
