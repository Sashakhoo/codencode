1.1 · What it is

Describing the outcome, not typing the syntax

Definition

Vibe coding

Building software by describing what you want to an AI assistant, then reviewing, running and refining what it produces. The word is casual; the discipline required is not.

Why this belongs in session 7 and not session 1

Because you now know what a function, a class, a file handle and a status code are. You can read what the model gives you and tell when it is wrong. Six weeks ago you could not, and it would have taught you nothing.

What it is genuinely good at

Boilerplate · a library you have never used · converting data between formats · writing tests · explaining an error message · a first draft of something tedious.

What it is bad at

Anything depending on context it cannot see · your specific data's quirks · deciding what to build · knowing when it is wrong. It will invent a function that does not exist, confidently.

The rule for this course, and for your career

You own every line in your repo. Not the model. If you cannot explain a line in a code review, it does not go in — no matter how well it appears to work.

Hands-on · Module 1

Rebuild a week4 function, both ways

15 minutes · pairs

Rebuild a week4 function, both ways

01Pick a function you wrote in week 4. Do not show it to the model.
02Describe what it should do and have the assistant write it.
03Diff the two versions. Where do they differ, and which is actually better?
04Find one thing the model's version does that you did not think of.
05Find one thing it got wrong, or one assumption it invented.
06Say out loud what you would keep from each. That judgement is the skill.
the comparison to make
# yours — you know exactly why every line is there
def total(cart):
    if not cart:
        return 0
    return sum(i["price"] * i["qty"] for i in cart)

# the model's — often broader, sometimes guessing
def total(cart):
    return sum(
        i.get("price", 0) * i.get("qty", 1)
        for i in cart or []
    )
# qty defaults to 1 — is that YOUR rule, or its guess?

That last comment is the whole lesson

The model made a reasonable business decision on your behalf, silently. Reading the code caught it. Not reading it would have shipped it.

What you would get back

Definition

A buildable prompt

One that states the data's shape, the constraints, and what must not break. Everything you leave out, the model invents.

The example is worth two of the others

One line of input and expected output removes almost all ambiguity — and lets the model check its own answer before handing it over.

2.2 · Debugging with it

Paste the whole error. Not your summary of it.

Give it the traceback verbatim

All of it — Session 4's call stack is exactly the information it needs. Paraphrasing throws away the file, the line number and the chain of calls.

Give it the code around the error

The failing function and anything it calls. An error on line 40 is frequently caused on line 12.

Say what you expected

"This should return 6.0 but returns 0" is a bug report. "It doesn't work" is not, for a human or a model.

Ask why, not just what

"Why does this happen?" teaches you something. "Fix it" gets you a patch you will not understand the next time it breaks.

a debugging prompt that actually works
I am getting this error in Python 3.12:

  Traceback (most recent call last):
    File "main.py", line 40, in <module>
      print(total(cart))
    File "main.py", line 12, in total
      return sum(i["price"] * i["qty"] for i in cart)
  KeyError: 'qty'

Here is the function and the data it is called with:
  [paste both]

I expected RM 6.00. Why is this happening, and what
is the smallest change that fixes it properly?
Notice how much of that you already know how to produce

Reading a traceback is Session 4. Knowing which data shape you passed is Session 3. The prompt is good because you understand the program — which is why this session comes last.

2.3 · Reviewing it

Four questions before any generated line stays

1 · Do I understand every line?

If not, ask it to explain that line. Then decide whether you need it at all — often you do not.

2 · Did it invent anything?

Made-up function names and parameters that do not exist are the classic failure. Run it; an ImportError or AttributeError tells you immediately.

3 · Does it handle my edge cases?

Empty input, missing key, zero, negative, no network. Test them yourself — it will usually claim it does.

4 · Is it doing more than I asked?

Extra features, extra dependencies, a config system you never wanted. Delete anything the brief does not call for.

the three-minute review, every single time
# 1 — does it even import?
python -c "import mymodule"

# 2 — the happy path
print(total([{"price": 2, "qty": 3}]))   # 6.0

# 3 — the edges YOU care about
print(total([]))                          # 0, not a crash
print(total([{"price": 2}]))            # your rule?

# 4 — read it once more, then commit
This is code review, which is a real job

Every professional team reviews code before it merges. You are doing the same thing — the author just happens to be a model that never gets tired and never says "I am not sure".

Hands-on · Module 2

The prompt-and-review drill

20 minutes · pairs

The prompt-and-review drill

01Write a six-part prompt for a feature you still need in your capstone. All six parts.
02Send it. Paste the result into your project and run it immediately.
03Run the four review questions from 2.3 against it, out loud, with your partner listening.
04Find at least one thing to change. There is always one.
05Commit it only once you can explain every line to your partner.
06Swap: your partner picks a random line and you explain it. That is the demo, rehearsed.
a six-part prompt, written out
I am a beginner writing Python 3, standard library only.

Write one function that reads expenses from a JSON file
and returns the total for a given month.

Input:  path (str), month (str, "2026-09")
Output: float, rounded to 2 decimals

The file holds a list of dicts with keys
"item", "amount", "date" (ISO format).

Handle: file missing (return 0.0), corrupt JSON
(return 0.0 and print a warning), no matching month.

Example: with one entry {"amount": 12.5,
"date": "2026-09-23"}, month "2026-09" -> 12.5

Add a docstring. No classes, no extra dependencies.

Read that prompt again

It is a specification. Writing it is most of the thinking — which is why people who can write it get good results and people who cannot, do not.

3.1 · Build order

Finish the spine before you decorate anything

OrderBuildWhy here
1Data shape + save/loadeverything else depends on it
2One feature, end to endyou now have a demo
3The menu or interfaceonly once there is something to drive
4Features two and threeeach one committed separately
5Error handlingthe three file tests, every network call
6Polishonly if 1–5 are genuinely finished
Build the thinnest end-to-end slice first

One path all the way through: input, process, store, show. Ugly is fine — once it runs you have a demo, and everything after is improvement rather than risk.

Stop adding on Thursday

Whatever is not working by Thursday night goes on the roadmap slide instead.

The trap, every single cohort

Somebody spends the whole week on a beautiful menu system for a program that cannot yet save a file. The menu is step three for a reason.

commit as you go — one per working feature
git add storage.py
git commit -m "Add save/load with missing-file handling"

git add main.py
git commit -m "Add expense entry from the menu"

3.2 · The demo

Five minutes — and half of it is the demo itself

The playhead runs the real timings. Notice how little room there is for anything but the demo.

problemlive demoarchitecturewhat broke

Rehearse it once, out loud, start to finish

Every demo that fails, fails in the first thirty seconds, on something nobody tried in order.

Have a screenshot ready

If the network dies or a file is missing mid-demo, a screenshot of it working keeps you moving. Professionals do this.

"What broke" is not a weakness

It is the most interesting thirty seconds of any demo. Telling people you hit a KeyError, found it in a traceback and fixed it proves the work is yours far better than a flawless run does.

3.3 · Where next

Seven weeks in — here is the map from here

Python Intermediate

Pythonic code, decorators and generators, advanced OOP, then NumPy, pandas, visualisation and statistics. The natural next step, and it assumes exactly what you now know.

Machine Learning

Feature engineering, regression, classification, neural networks, LSTMs and a capstone. Session 6's JSON and Session 3's data structures are the entry ticket.

Keep building, publicly

One small finished project a month, on GitHub, with a README. Three of them is a portfolio, and a portfolio outperforms any certificate in an interview.

The habit that matters most

Read other people's code. Open a small library you use and read it. It is the fastest way to stop writing like a beginner.
