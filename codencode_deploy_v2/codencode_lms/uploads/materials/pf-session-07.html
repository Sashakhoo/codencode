1.1 · The user

“People” is not a user. Name one.

Definition

Persona

One specific, named, imaginary person who stands in for a whole group of real users. You give them a device, a context, a level of patience and one thing they are trying to get done.

Why one name beats a description

"Teachers are busy" changes nothing. "Farah has 90 seconds and one hand free" rules out a form with six fields — the persona makes design decisions for you.

Three personas, one MVP

You list every user you can think of, then build for one. The other two get their features in Out of Scope — which is Session 6's scoping board, applied to people instead of features.

1.1b · User stories

One sentence, three clauses, and a test

Definition

User story

One sentence in a fixed shape: As a <role>, I want <capability>, so that <benefit>. The third clause is the one everybody skips and the one that stops you building the wrong feature.

stories, with acceptance criteria
US-1  As a teacher, I want to mark a student present
      in one tap, so that I can finish the register
      before the next class starts.

  Given I am on the register for today’s class
  When  I tap a student’s name
  Then  their status toggles and is saved at once
  And   the page still works if I lose signal

US-2  As a parent, I want to see last month’s
      attendance, so that I know my son is going.

Why Given / When / Then

It converts an opinion into a test. "It should be easy to use" cannot be checked by anyone. "Given the register is open, when I tap a name, then the status saves" either happens or it does not.

The “so that” clause is the filter

If you cannot finish it, the feature has no reason to exist. Half the features that get cut in Module 1 are cut by trying to write that clause and failing.

Definition

Functional requirement

Something the system does, written so it can be demonstrated. Numbered, testable, and traceable back to a user story.

The test for a good FR

Could you write a checklist item that a stranger could tick? If not, it is either too vague or it is actually non-functional.

1.2b · Writing FRs

Numbered, testable, traceable

the functional requirements for the Class Tracker
FR-1  The system shall let a teacher mark a student
      present, absent or late for a given class date.
      [from US-1]

FR-2  The system shall save a mark immediately and
      show a confirmation within 1 second. [US-1]

FR-3  The system shall prevent two marks for the same
      student on the same date. [US-1]

FR-4  The system shall show a parent the attendance
      history for their own child only. [US-2]

FR-5  The system shall let a teacher export a class
      register for a month as CSV. [US-3]

FR-6  The system shall record homework with a title
      and a due date, visible to students. [US-4]

“The system shall” is not pretentious

It is the phrase the whole industry uses because it forces a subject and a verb. The moment you write "it would be nice if…" you have written a wish, not a requirement.

Three is still the limit

Six FRs are listed above; your MVP gets three. Session 6's scoping board applies unchanged — the other three go in Out of Scope and become your roadmap slide.

1.3 · Non-functional

The requirements that get you fired, not praised

Definition

Non-functional requirement

A constraint on how well the system works rather than what it does. Performance, security, usability, reliability, portability, legal. Each one must carry a number or it is an opinion.

CategoryBad (unmeasurable)Good (testable)
Performance"must be fast"register loads in < 2s on 4G
Security"must be secure"only the assigned teacher may edit a register
Usability"easy to use"a teacher marks 12 students in < 60s
Reliability"no crashes"no data loss if signal drops mid-save
Portability"works everywhere"Chrome and Safari on a phone, no install
Legal—student data stored in Malaysia, PDPA-compliant

The two beginners always forget

Security — because the app works fine when you are the only user. And legal — because PDPA applies the moment you store somebody's child's name, and "I did not know" is not a defence.

Why NFRs decide the architecture

"Works on a phone with no install" rules out a desktop app. These constraints choose your stack before you write a line.

1.3b · Writing NFRs

Every one of them carries a number

the NFRs for the Class Tracker, written properly
NFR-1 Any page shall render in under 2 seconds on a
      4G connection.

NFR-2 A register shall be editable only by the teacher
      assigned to that class.

NFR-3 A parent shall see only their own child’s data.

NFR-4 No attendance mark shall be lost if the browser
      is closed after the confirmation appears.

NFR-5 The app shall work on a phone browser with no
      installation.

NFR-6 Personal data shall be held in Malaysia and
      handled in line with the PDPA 2010.

Read NFR-4 again

"No mark shall be lost if the browser is closed after the confirmation appears." That single sentence decides that you save before you show the tick — an architecture decision, written as a requirement.

How to test an NFR

Throttle your browser to 4G in DevTools for NFR-1. Log in as the wrong teacher for NFR-2. Turn off wi-fi mid-save for NFR-4. If you cannot think of the test, the NFR is not measurable yet.

NFRs are where professional work shows

Anybody can build the happy path. The difference between a student project and a product is entirely in this list — and it is the part nobody demos, so say it out loud when you present.

Where your six sessions live

LOGIC is the box you already know how to fill. Functions, classes, error handling, files — all of it. The other three boxes are plumbing around it.

The rule that keeps it sane

The frontend never touches the database. Everything goes through the API, so all your rules live in one place — which is Session 5's encapsulation, applied to a whole system.

2.2 · Designing the API

The contract between the two halves

Definition

API endpoint

One URL plus one HTTP verb, with an agreed request shape and response shape. Together your endpoints are the only way the frontend can do anything.

VerbRouteDoesReturns
GET/classes/{id}/registertoday's register200 + list
POST/attendancemark a student201 + {id}
PATCH/attendance/{id}change a mark200
DELETE/attendance/{id}remove a mark204
GET/students/{id}/historya parent's view200 + list

Routes are nouns, verbs are verbs

POST /attendance, never POST /createAttendance. The verb is already in the HTTP method — repeating it in the URL is the most common beginner tell.

Design the routes before you write any code

The route table is the contract. Once it exists the two halves can be built independently — by two people, or by you on two evenings.

2.2b · The two halves

Twenty lines of Python, ten of JavaScript

the backend — FastAPI, shorter than you expect
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI()

class Mark(BaseModel):          # the request shape
    student_id: int
    status: str               # present | absent | late

@app.post("/attendance", status_code=201)
def mark(m: Mark):
    """FR-1: record one attendance mark."""
    if m.status not in {"present", "absent", "late"}:
        raise HTTPException(422, "bad status")
    if already_marked_today(m.student_id):      # FR-3
        raise HTTPException(409, "already marked")
    new_id = save(m.student_id, m.status)
    return {"id": new_id, "status": m.status}
Notice the docstring

"""FR-1: record one attendance mark.""" — every endpoint names the requirement it satisfies. Six months later that line tells you why the function exists and whether it is still needed.

the frontend — plain JavaScript, no framework needed
async function mark(studentId, status) {
  const r = await fetch("/attendance", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ student_id: studentId, status })
  });
  if (!r.ok) { alert("Could not save"); return; }
  const data = await r.json();
  document.getElementById("s"+studentId).textContent = "✓";
}

Three lines of that JavaScript are the whole frontend job

Send JSON · check r.ok · update the screen. Everything else a framework offers is convenience you do not need this week.

2.3 · Vibe coding

The loop, and the four questions before anything stays

Definition

Vibe coding

Building software by describing what you want to an AI assistant, then reviewing, running and refining what it produces. The word is casual; the discipline required is not.

Small loops, not big ones

Ask for one function or one endpoint, never one application. A tight loop you can check at every turn beats a thousand-line answer you will never fully read.

1 · Do I understand every line? 2 · Did it invent anything?

If you cannot explain a line, ask it to — then decide whether you need it at all. And made-up function names are the classic failure: run it, and an ImportError tells you at once.

3 · Does it handle my edge cases? 4 · Is it doing more than I asked?

Your FRs already name the edges — duplicate mark, unknown student, lost signal. Test them yourself. Then delete every endpoint, dependency and config option the spec did not ask for.

You own every line in your repo

Not the model. In the demo you will be asked about a line chosen at random, and "the AI wrote that" is not an answer.

What you would get back

Definition

A buildable prompt

One that states the stack, the one thing to build, the data shapes, the rules, the edge cases and one example. Everything you leave out, the model invents.

Your FR line is most of the prompt already

"FR-3: the system shall prevent two marks for the same student on the same date" is the edge-case clause. Module 1 was not paperwork — it was prompt engineering with a different name.

3.1b · Prompts 1 & 2

Scaffold the project, then one endpoint

PROMPT 1 · scaffold the project
I am a beginner building a small web app in Python 3.12.
Stack: FastAPI + uvicorn + SQLite, standard library
elsewhere, no ORM, no frontend framework.

Create the folder structure and empty files for:
  main.py      FastAPI app and routes only
  models.py    dataclasses for Student, Attendance
  storage.py   all SQLite access, nothing else
  static/      index.html, app.js, style.css

Show me the tree and the contents of main.py with a
single GET /health endpoint. Nothing else yet.
PROMPT 2 · one endpoint, from one FR
Python 3.12, FastAPI, SQLite via sqlite3.

Write ONE endpoint: POST /attendance

Request body: {"student_id": int, "status": str}
status must be one of present | absent | late.
Response 201: {"id": int, "status": str}

Rules:
  - unknown student_id  -> 404
  - invalid status      -> 422
  - already marked today for that student -> 409,
    and do NOT create a second row   [FR-3]

Example: POST {"student_id":12,"status":"present"}
         -> 201 {"id":4471,"status":"present"}

Add a docstring naming the FR. No extra endpoints.
3.1c · Prompts 3 & 4

The frontend, and the one for when it breaks

PROMPT 3 · the frontend for that endpoint
Plain HTML + CSS + vanilla JavaScript. No framework,
no build step, no npm. Must work in a phone browser.

Build the register screen for a teacher:
  - a list of 12 student names
  - tapping a name POSTs to /attendance and shows a
    tick next to it
  - if the request fails, show an inline message and
    leave the row untouched  [NFR-4]

Dark theme, large tap targets, one file per concern.
PROMPT 4 · the debugging prompt
Python 3.12, FastAPI. I get this error:

  [paste the FULL traceback, not a summary]

Here is the endpoint and the function it calls:
  [paste both]

I expected a 409 for a duplicate mark; I got a 500.
Why is this happening, and what is the smallest
change that fixes it properly?

Notice what all four have in common

A stack, one job, the shapes, the rules, an example. And the rules are lifted from your FRs and NFRs word for word.

Paste the whole traceback

All of it, verbatim. Session 4's call stack is exactly the information the model needs — paraphrasing throws away the file, the line number and the chain of calls.

Ask why, not just what

"Why does this happen?" teaches you something you keep. "Fix it" gets you a patch you will not understand the next time it breaks — and it will break again.

3.2 · Build order

Finish the spine before you decorate anything

Build the thinnest end-to-end slice first

One path that goes all the way through: tap, request, validate, save, respond, update. Ugly is fine. Once that runs you have a demo, and everything after it is improvement rather than risk.

Why the frontend is step three

An endpoint you can test in /docs proves the logic with no UI at all. Build the button first and any bug could be in either half.

The trap, every single cohort

Somebody spends the week on a beautiful frontend for an API that cannot yet save a row. The frontend is step three for a reason.

commit as you go — one per working requirement
git commit -m "FR-1: POST /attendance saves a mark"
git commit -m "FR-3: duplicate mark returns 409"
git commit -m "NFR-4: inline error, row untouched"

# the message names the requirement, so the
# history IS your progress report
Ask early

Stuck for more than 40 minutes, message the group. Being stuck quietly for four days is the single most common reason a capstone does not get finished.

3.3 · The demo

Five minutes — and half of it is the demo itself

The playhead runs the real timings. Notice how little room there is for anything but the demo.

the userlive demoarchitecturewhat broke

Open with the person, not the tech

"Cikgu Farah has 90 seconds between classes" lands. "I built a FastAPI backend" does not — and the architecture slide is 60 seconds later anyway.

Rehearse it once, out loud, in order

Every demo that fails, fails in the first thirty seconds, on something nobody tried in sequence. Have a screenshot ready in case the network dies.

“What broke” is not a weakness

It is the most interesting thirty seconds of any demo. A 500 you traced to a missing UNIQUE constraint proves the work is yours far better than a flawless run does.
