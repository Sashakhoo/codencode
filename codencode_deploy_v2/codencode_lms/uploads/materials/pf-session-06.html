1.1 · Persistence

Memory forgets. Disk does not.

Definition

Persistence

Data that survives the program ending. Variables live in memory, which the operating system reclaims the moment your process exits. A file lives on disk until something deletes it.

FormatBest forOpened by
.txtlogs, notes, anything line-by-lineanything
.csvrows and columnsExcel, Sheets, pandas
.jsonnested structure — lists of dictsevery language, every API
SQLitelarge data, searching, concurrent writesPython Intermediate
Pick by the shape of your data

Flat rows with the same columns every time → CSV. Anything nested, optional or varied → JSON. If you are inventing your own text format, stop — one of these already does it.

Where the file actually goes

open("data.txt") looks in the directory you ran the script from, not the one the script lives in. This confuses everyone once. pathlib.Path(__file__).parent is the fix.

the absolute minimum
# write — "w" replaces everything in the file
with open("notes.txt", "w") as f:
    f.write("first line\n")

# read it back
with open("notes.txt") as f:
    print(f.read())

1.3 · CSV & JSON

Teacher Demo — the expense log

CSV — rows and columns, readable in Excel
import csv

# append one row (newline="" avoids blank lines)
with open("expenses.csv", "a", newline="") as f:
    csv.writer(f).writerow(["2026-09-23", "Lunch", 12.50])

# read it back as dictionaries — much nicer
with open("expenses.csv", newline="") as f:
    for row in csv.DictReader(f):
        print(row["item"], row["amount"])
# note: every value arrives as a STRING
JSON — nested structure, straight from your objects
import json

def save(items, path="expenses.json"):
    """Write every expense to disk."""
    with open(path, "w") as f:
        json.dump(items, f, indent=2)

def load(path="expenses.json"):
    """Read expenses, or start empty on the first run."""
    try:
        with open(path) as f:
            return json.load(f)
    except FileNotFoundError:
        return []
    except json.JSONDecodeError:
        print("File is corrupt — starting fresh.")
        return []

Two excepts, two different disasters

FileNotFoundError is the first ever run — normal, start empty. JSONDecodeError means the file exists but is damaged — worth telling the user about rather than silently wiping it.

Saving an object is not automatic

json.dump handles dicts, lists, strings and numbers — not your objects. Give each class a to_dict() method.

round-tripping an object
class Expense:
    def __init__(self, item, amount, date):
        self.item, self.amount, self.date = item, amount, date

    def to_dict(self):
        return {"item": self.item,
                "amount": self.amount,
                "date": self.date}

    @classmethod
    def from_dict(cls, d):
        return cls(d["item"], d["amount"], d["date"])

save([e.to_dict() for e in items])
items = [Expense.from_dict(d) for d in load()]

Those three tests are the whole exercise

Works · file missing · file corrupt. Any program that reads a file must survive all three, and almost every beginner project only handles the first.

2.1 · The round trip

What just happened

—

Definition

API

A program on someone else's machine that answers questions over the internet. You send a URL; it sends back data — almost always JSON.

The number you must check

2xx worked · 4xx your mistake (wrong URL, bad key, too many requests) · 5xx their mistake. Calling .json() on a 404 crashes.

2.2 · requests

Calling a real API — no key required

install once, then use everywhere
# in your terminal
pip install requests
live weather for Johor Bahru
import requests

URL = "https://api.open-meteo.com/v1/forecast"
params = {
    "latitude": 1.4927,
    "longitude": 103.7414,
    "current": "temperature_2m,relative_humidity_2m",
}

r = requests.get(URL, params=params, timeout=10)
print(r.status_code)     # 200

data = r.json()            # dict — Session 3 shapes
now  = data["current"]
print(f"JB is {now['temperature_2m']} degC")
Everything you need you already know

The response is a dictionary of dictionaries and lists — exactly Session 3. The only new idea is that it arrived over a network instead of from a file, and that the network can fail.

Explore before you code

Paste the URL into a browser first and look at the JSON. Then print(data.keys()) in Python. Two minutes of looking saves twenty minutes of guessing key names.

2.3 · When it fails

The network fails. Write the code that expects it.

the shape every API call should have
import requests

def get_weather(lat, lon):
    """Current temperature, or None if it could not be fetched."""
    try:
        r = requests.get(URL, params={...}, timeout=10)
    except requests.Timeout:
        print("The server took too long.")
        return None
    except requests.ConnectionError:
        print("No internet connection.")
        return None

    if r.status_code != 200:
        print(f"Server said {r.status_code}.")
        return None

    return r.json()["current"]["temperature_2m"]

Always pass a timeout

Without one, requests will wait forever if the server never answers — and your program simply hangs with no error to read.

Never commit an API key

A key in a GitHub repo is found by bots within minutes. Put it in a .env file, add that to .gitignore, and read it with os.environ.

Be polite to other people's servers

Most free APIs allow a few hundred calls a day. Do not call one inside a loop that runs a thousand times — cache the answer in a file and re-use it. Getting blocked mid-project is a miserable way to lose a weekend.

if temp is None:
    print("Could not fetch — nothing logged.")

The rule that saves capstones

3.2 · The brief

One page. Written today, before the enthusiasm fades.

SectionWhat goes in it
ProblemOne sentence: whose problem, and what it costs them now.
UserWho runs this. Be specific — "students in JB", not "people".
MVP featuresThree, maximum. Each one a verb.
DataWhere it comes from and where it is stored — file, format, API.
Out of scopeWhat you are deliberately not building. Be generous here.
DemoThe exact sequence you will show in week 7.
The out-of-scope section is the important one

It is what you point at when, on Thursday night, you get the brilliant idea that would take another eight hours. Writing it down now is how you give yourself permission to say no later.

A worked example

Problem: students lose track of small daily spending. User: a student with a phone and a laptop. MVP: add an expense · list this month · show the total. Data: a local JSON file. Out of scope: categories, charts, accounts, cloud sync, mobile. Demo: add three expenses live, show the total, restart the app, show they are still there.

3.3 · Planning week 7

What good looks like next Saturday

Before next session

Repo created, folder structure in place, README holding your brief, and one feature working end to end — even badly.

The 60/40 split

Spend 60% of your time on the feature that makes the demo work, and 40% on everything else. Most people invert this and spend the week on a beautiful menu for a program that does nothing.

Commit as you go

A commit per working feature. A week of work in one commit on Friday night is how people lose everything to one bad edit.

Ask early

If you are stuck for more than 40 minutes, message the group. Being stuck quietly for four days is the single most common reason a capstone does not get finished.

DayAim
TonightRepo, structure, README with the brief. 30 minutes.
Mid-weekFeature one works and is committed.
ThursdayFeatures two and three. Stop adding anything new.
FridayError handling and the three file tests.
SaturdayRehearse the demo once, out loud, start to finish.
Rehearsing is not optional

Every demo that goes wrong goes wrong in the first thirty seconds, on something the person never actually tried in order. Run it once, exactly as you will show it.
