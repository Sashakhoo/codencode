One job you can name in a sentence with no "and" in it — and it returns a value rather than printing.

Where does a local variable go?

It is destroyed the moment the function returns. Touch it afterwards and you get a NameError.

The data and the code have drifted apart

acc = {"owner": "Aisyah", "balance": 500}

def withdraw(account, amount):

Definition

Object

One thing that carries its own data and knows its own behaviour. The balance and the code that may change it live in the same place, so the code can enforce the rules.

where you will be by the end of today
acc = Account("Aisyah", 500)

The argument in one line

If the only way to change a balance is a method you wrote, then every rule about balances is enforced in one place — and impossible to forget.

1.3 · self

self, and the three lines everyone gets wrong first

Definition

self

The object the method was called on. Python passes it automatically: a.deposit(100) becomes Account.deposit(a, 100) behind the scenes.

the full class, with methods
class Account:
    """A bank account with an owner and a balance."""

    def __init__(self, owner, balance=0):
        self.owner = owner        # attribute
        self.balance = balance

    def deposit(self, amount):
        """Add money. Refuses zero or negative."""
        if amount <= 0:
            return False
        self.balance += amount
        return True

    def withdraw(self, amount):
        """Take money out if there is enough."""
        if amount > self.balance:
            return False
        self.balance -= amount
        return True

Mistake 1 — forgetting self in the definition

def deposit(amount): gives you takes 1 positional argument but 2 were given. Python passed the object; your definition had no room for it.

Mistake 2 — forgetting self inside the body

balance += amount creates a local variable that dies at the return. The object never changes and there is no error at all — the worst kind of bug.

Mistake 3 — calling __init__ yourself

You never write acc.__init__(). Writing Account("Aisyah", 500) calls it for you.

__init__ is a setup, not a constructor

Python has already made the empty object by the time it runs — its job is filling in the attributes, which is why it returns nothing.

2.1 · Inheritance

A child gets everything the parent has

The animation loops between the two children. Both get deposit and withdraw free.

parent — AccountSavingsAccountCurrentAccount
What just happened

—

Definition

Inheritance

A class built on top of another. The child starts with every attribute and method the parent has, and only writes what is different.

The honest warning

Inheritance is over-used by beginners. Only reach for it when the child genuinely is a kind of the parent. A Car is a Vehicle — fine. A Car has an Engine, so Engine is not a parent of Car.

2.2 · super()

Overriding, and extending rather than replacing

the child classes
class SavingsAccount(Account):
    """An Account that earns interest."""

    def __init__(self, owner, balance=0, rate=0.03):
        super().__init__(owner, balance)   # parent setup
        self.rate = rate                  # then the extra

    def add_interest(self):
        """Apply one period of interest."""
        self.balance += self.balance * self.rate


class CurrentAccount(Account):
    """An Account allowed to go overdrawn."""

    def __init__(self, owner, balance=0, overdraft=1000):
        super().__init__(owner, balance)
        self.overdraft = overdraft

    def withdraw(self, amount):        # overrides
        if amount > self.balance + self.overdraft:
            return False
        self.balance -= amount
        return True
Definition

super()

A reference to the parent class. super().__init__(...) runs the parent's setup so you do not copy those lines into every child.

Override means replace, super means extend

CurrentAccount.withdraw replaces the parent's entirely. If you only wanted to add something — logging, say — you would call super().withdraw(amount) inside your version and build around it.

Forgetting super().__init__

The child's own attributes get set, the parent's do not, and the first method that touches self.balance raises AttributeError. Always call it first.

2.3 · Dunder methods

Teacher Demo — making your object behave like a built-in

without __str__
a = Account("Aisyah", 500)
print(a)
# <__main__.Account object at 0x7f8b1c0d2e50>
# technically true, completely useless
with __str__
class Account:
    ...
    def __str__(self):
        """How this account looks when printed."""
        return f"{self.owner}: RM {self.balance:,.2f}"

print(a)        # Aisyah: RM 500.00
MethodTriggered byShould return
__init__Account(...)nothing
__str__print(obj), str(obj)a readable string
__repr__the REPL, a list of objectsa precise string
__len__len(obj)an int
__eq__a == bTrue / False
Dunder is just "double underscore"

You never call these directly. You write them, and Python calls them when someone uses the ordinary syntax — which is how your own class starts to feel like part of the language.

Write __str__ on every class

It costs two lines and it makes every print, every log line and every debugging session readable. It is the highest-value habit in this session.

3.1 · Encapsulation

Guarded or not — try to break the balance

Switch to UNGUARDED and set the balance directly — nothing stops it going to RM -9,999.

guardedrefused / broken
Definition

Encapsulation

Keeping an object's data reachable only through its own methods, so the object can enforce its rules and you cannot put it into an impossible state.

the convention
def __init__(self, owner, balance=0):
    self.owner = owner
    self._balance = balance   # _ = internal

@property
def balance(self):
    return self._balance   # read-only

Python trusts you

A leading underscore is a convention, not a lock. Python will not stop you — the community treats ignoring it as your own fault.

3.2 · Composition

has-a beats is-a more often than you would think

Definition

Composition

Building a class out of other objects it owns, instead of inheriting from them. A Bank has Accounts; it is not a kind of Account.

composition in practice
class Bank:
    """Holds many accounts and can report on them."""

    def __init__(self, name):
        self.name = name
        self.accounts = []       # has-a

    def open_account(self, owner, opening=0):
        acc = Account(owner, opening)
        self.accounts.append(acc)
        return acc

    def total_held(self):
        return sum(a.balance for a in self.accounts)

    def __len__(self):
        return len(self.accounts)
The test that decides it

Say it out loud. "A SavingsAccount is an Account" — true, so inherit. "A Bank is an Account" — nonsense, so compose. If the sentence sounds wrong, the inheritance is wrong.

Why this matters in practice

Deep inheritance chains are the most common way an OOP codebase becomes unreadable. Three classes deep and nobody can say where a method actually came from. Composition stays flat.

using it
b = Bank("CodenBank")
b.open_account("Aisyah", 500)
b.open_account("Kumar", 1200)

print(len(b))            # 2 — because of __len__
print(b.total_held())  # 1700
3.3 · When not to

Not everything should be a class

Use a class when…

The thing has state that changes over time and rules about how it may change. An account, a game character, a shopping cart, a connection.

Use a plain function when…

You are transforming input into output with nothing to remember. calculate_tax(income) does not need an object.

Use a dictionary when…

It is just data being carried around, with no behaviour attached. A row from a CSV, a config, a JSON response.

The smell to watch for

A class with an __init__ and exactly one other method that you call once. That is a function wearing a costume.

the same job, three honest ways
# 1 — a function. Correct: nothing to remember.
def tax(income):
    return income * 0.06

# 2 — a dict. Correct: data, no rules.
row = {"name": "Aisyah", "city": "JB"}

# 3 — a class. Correct: state AND rules.
class Account:
    def withdraw(self, amount): ...

# the wrong version of 1:
class TaxCalculator:
    def __init__(self, rate): self.rate = rate
    def calc(self, income): return income * self.rate
# a function with extra steps
Judgement is the outcome, not syntax

Anyone can learn class in ten minutes. Knowing when it earns its keep is the part that takes a career — and LO5 is asking you to start.

Your Turn — design your own hierarchy

a worked skeleton to copy the shape of
class LibraryItem:
    """Anything the library lends out."""
    def __init__(self, title, days=14):
        self.title = title
        self.days = days
        self._out = False

    def borrow(self):
        if self._out: return False
        self._out = True; return True

    def __str__(self):
        return f"{self.title} ({self.days}d)"

class DVD(LibraryItem):
    def __init__(self, title):
        super().__init__(title, days=3)

class Reference(LibraryItem):
    def borrow(self):
        print("Reference items stay in the library.")
        return False

Before you write a line, say the sentences

"A DVD is a LibraryItem." "A Reference book is a LibraryItem." Both true, so the hierarchy is sound. If you cannot say it, do not build it.
