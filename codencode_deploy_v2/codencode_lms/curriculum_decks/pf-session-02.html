1.1 · Why decisions

Every useful program branches

Definition

Conditional

A piece of code that runs only if something is true. It is how a program stops doing the same thing every time and starts responding to what it is given.

What changed since last week

Session 1's scripts ran every line, top to bottom, in order. That is fine for a calculator that always does the same sum — but useless for anything that has to react. An ATM that dispenses cash regardless of the PIN is not an ATM.

Where you have already met one today

Your phone decided whether to show a notification. The toll gate decided whether your Touch 'n Go had enough balance. Grab decided which driver was nearest. All conditionals.

the shape of every decision
if <something that is True or False>:
    # this runs only when it is True
    do_something()

# indentation is not decoration —
# it is how Python knows what is inside the if

The colon and the indent

Forget the : and you get a SyntaxError. Forget the indent and you get an IndentationError. Both are among the most common first-month errors — and both are obvious once you read the message.

= versus ==

One equals sign assigns: score = 80 puts 80 in the box. Two equals signs ask: score == 80 gives True or False. Mixing them up is the single most common conditional bug.

and / or, and why order can matter
age = 17
has_licence = False

print(age >= 18 and has_licence)   # False — both must hold
print(age >= 18 or  has_licence)   # False — neither holds
print(not has_licence)            # True

# chaining works and reads nicely
print(60 <= score < 80)          # True if in the B band
The chained form is worth learning

60 <= score < 80 does what the maths notation suggests, and most other languages cannot do it. It is clearer than score >= 60 and score < 80 and harder to get wrong.

the boundary bug, and the fix
# WRONG — what grade does exactly 80 get?
if score > 80:
    grade = "A"
elif score > 60:
    grade = "B"

# 80 falls through to the elif and gets a B.

# RIGHT
if score >= 80:
    grade = "A"
elif score >= 60:
    grade = "B"
Always test the edges

Not 85 and 45 — those work in almost any version. Test exactly 80, exactly 60, one below each. Two minutes of that finds bugs that survive a hundred random tests.

2.1 · Guard clauses

Flatten it — your future self will thank you

before — four levels deep
def withdraw(user, amount):
    if user.active:
        if user.balance >= amount:
            if amount > 0:
                user.balance -= amount
                return True
            else:
                return False
        else:
            return False
    else:
        return False
after — guard clauses
def withdraw(user, amount):
    if not user.active:
        return False
    if user.balance < amount:
        return False
    if amount <= 0:
        return False

    # the real work, unindented
    user.balance -= amount
    return True
Definition

Guard clause

A check at the top of a function that deals with a bad case and returns immediately, so the rest of the function can assume everything is fine.

The rule of thumb

Handle the failures first and get out. What is left at the bottom is the thing the function is actually for — and it sits at one level of indentation instead of four.

2.2 · Bad input

Someone will type "sixty" into your number box

Why this belongs in a conditionals lesson

Because the naive fix is a conditional, and it does not work. You cannot check "is this text a number?" with if alone — you have to try it and catch the failure.

what happens, and the fix
age = int(input("Age? "))
# user types "sixty" -> ValueError

# the fix — try it, catch the failure
try:
    age = int(input("Age? "))
except ValueError:
    print("Please type a whole number.")
    age = None
the pattern you will reuse all course
def ask_number(prompt):
    while True:
        try:
            return float(input(prompt))
        except ValueError:
            print("Numbers only — try again.")

A preview, not the full lesson

Error handling properly is Session 6. Today you need just enough that your ATM and tax calculator do not crash when someone fat-fingers a letter — because the homework rubric checks exactly that.

2.3 · Reading logic

Teacher Demo — the grade report generator

read this before you run it — what does 85 print?
def report(name, score):
    if score < 0 or score > 100:
        return f"{name}: invalid score"

    if score >= 80:
        grade, note = "A", "excellent"
    elif score >= 60:
        grade, note = "B", "good"
    elif score >= 40:
        grade, note = "C", "passed"
    else:
        grade, note = "F", "resit needed"

    star = " *" if score >= 95 else ""
    return f"{name}: {grade} ({note}){star}"
Definition

Ternary expression

a if condition else b — a one-line if/else that produces a value. Good for short choices; bad for anything you would have to read twice.

Note the guard clause at the top

The invalid-score check returns immediately, so the grade logic below never has to worry about nonsense input. That is 2.1 applied to a real function.

run it on the edges
for s in [100, 95, 94, 80, 79, 60, 40, 0, -5, 105]:
    print(report("Aisyah", s))

3.1 · ATM lock

Three attempts, then the card is kept

Watch the attempts burn down. Press CORRECT PIN mid-way and the counter resets.

attempt usedstill available
Definition

Counter pattern

A variable that starts at zero and increases each time something happens, with a conditional watching it. The backbone of retry limits, scoring, and anything that counts.

The three pieces

A counter from 0 · a loop that asks again · a conditional that stops at 3. Miss one and it either never locks or locks at once.

The bug to expect

Checking the lock before incrementing gives four attempts instead of three. One-line fix, twenty minutes to find if you are not testing as you go.

3.3 · Debugging

Four conditional bugs, and how to spot each

1 · Wrong boundary operator

> where you meant >=. Symptom: exactly one value gets the wrong answer. Test every boundary.

2 · Branches in the wrong order

A narrower condition placed after a wider one never runs. Symptom: a branch that looks correct but is never reached. Print inside it to confirm.

3 · = instead of ==

Python catches this with a SyntaxError inside an if — which is lucky, because in many languages it silently assigns and passes.

4 · Forgetting else

If nothing matches, nothing happens — silently. Symptom: no output and no error. Always have an else, even if it only prints "unexpected input".

the debugging move that finds all four
if score >= 80:
    print("DEBUG: took the A branch")   # ← temporary
    grade = "A"
elif score >= 60:
    print("DEBUG: took the B branch")
    grade = "B"
else:
    print("DEBUG: fell through to else")
    grade = "F"

# run it, read which branch fired, delete the prints
Print which branch ran

You are never guessing about conditionals — you can always just ask the program which path it took. Thirty seconds of temporary prints beats twenty minutes of staring.

tax — the structure that keeps it honest
income = ask_number("Annual income? RM ")

bands = [
    (0,     5000,  0.00),
    (5000,  20000, 0.01),
    (20000, 35000, 0.03),
    (35000, 50000, 0.06),
    (50000, float("inf"), 0.11),
]

total = 0
for low, high, rate in bands:
    in_band = max(0, min(income, high) - low)
    total += in_band * rate
    if in_band > 0:
        print(low, high, rate, in_band)

print(f"Total: RM {total:,.2f}")

The min/max line is the whole trick

max(0, min(income, high) - low) gives exactly how much of your income sits inside that band — 0 if you never reached it, the full band if you passed straight through.
